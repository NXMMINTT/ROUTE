## โจทย์ที่แก้

มีคลังสินค้า (depot) 1 แห่ง และลูกค้าหลายราย แต่ละรายต้องการของไม่เท่ากัน (demand) ต้องตัดสินใจว่า

- รถคันไหนไปส่งลูกค้ารายใด
- แต่ละคันวิ่งไปตามลำดับไหน (ออกจาก depot → ส่งของ → กลับ depot)

โดยมีเงื่อนไข

- ของที่รถแต่ละคันบรรทุกรวมกันต้องไม่เกินความจุ (capacity)
- ลูกค้าทุกรายได้รับของครบ และได้รับจากรถคันเดียว

เป้าหมายคือ **ระยะทางรวมของรถทุกคันสั้นที่สุด** ผลลัพธ์วัดด้วย **gap** เทียบกับค่า optimal
(ระยะที่ดีที่สุดที่เคยมีคนหาได้) เกณฑ์ของการแข่งขันคือ **gap ต่ำกว่า 5%**

2. เลือกเวลาค้นหา (5 / 10 / 30 วินาที)

   - **การ์ดรถรายคัน:** % การบรรทุกเทียบความจุ และลำดับการวิ่ง `DEPOT → 12 → 5 → … → DEPOT`

ผลล่าสุดจำไว้ในแท็บนั้น สลับไปหน้า 3D แล้วจะเห็นผลเดิมโดยไม่ต้องอัปโหลดซ้ำ

## รูปแบบไฟล์ที่อัปโหลดได้

ขนาดไม่เกิน 1 MB ต่อไฟล์ และไม่เกิน 2,000 จุด

### `.vrp` / `.txt` — รูปแบบ CVRPLIB

```
NAME : A-n32-k5
COMMENT : (Augerat et al, No of trucks: 5, Optimal value: 784)
TYPE : CVRP
DIMENSION : 32
EDGE_WEIGHT_TYPE : EUC_2D
CAPACITY : 100
NODE_COORD_SECTION
 1 82 76
 2 96 44
 ...
DEMAND_SECTION
1 0
2 19
 ...
DEPOT_SECTION
 1
 -1
EOF
```

| ส่วน | ความหมาย | จำเป็น |
|---|---|---|
| `NAME` | ชื่อ instance ใช้เป็นชื่อในคลัง Benchmark | ไม่ (ไม่มี = ใช้ชื่อไฟล์) |
| `COMMENT` → `No of trucks: N` | จำนวนรถ | ไม่ |
| `COMMENT` → `Optimal value: N` | ค่า optimal สำหรับคิด gap | ไม่ |
| `EDGE_WEIGHT_TYPE` | ต้องเป็น `EUC_2D` หรือ `EXACT_2D` | ไม่ (ไม่มี = EUC_2D) |
| `CAPACITY` | ความจุรถต่อคัน | **ใช่** |
| `NODE_COORD_SECTION` | `id x y` ของทุกจุด | **ใช่** |
| `DEMAND_SECTION` | `id demand` ของทุกจุด (depot = 0) | **ใช่** |
| `DEPOT_SECTION` | id ของ depot ปิดท้ายด้วย `-1` | ไม่ (ไม่มี = จุด 1) |

ถ้าไม่ได้ระบุจำนวนรถใน COMMENT ระบบจะอ่านจากเลขหลัง `-k` ในชื่อแทน เช่น `A-n32-k5` = 5 คัน

### `.csv` / `.xlsx` — ตารางจาก Excel

แถวแรกเป็นหัวคอลัมน์ **แถวข้อมูลแถวแรกคือคลังสินค้า (depot)** แถวถัดไปคือลูกค้า

| id | x | y | demand | capacity | vehicles | name |
|---|---|---|---|---|---|---|
| 1 | 82 | 76 | 0 | 100 | 5 | my-sites |
| 2 | 96 | 44 | 19 | | | |
| 3 | 50 | 5 | 21 | | | |

| คอลัมน์ | ความหมาย | จำเป็น |
|---|---|---|
| `x`, `y` | พิกัด | **ใช่** |
| `demand` | ปริมาณที่ลูกค้าต้องการ (จำนวนเต็ม) | **ใช่** |
| `capacity` | ความจุรถ ใส่แถวเดียวพอ | **ใช่** |
| `id` | เลขจุด (จำนวนเต็มบวก ไม่ซ้ำ) | ไม่ (ไม่ใส่ = 1, 2, 3, … ตามลำดับแถว) |
| `vehicles` | จำนวนรถ ใส่แถวเดียวพอ | ไม่ |
| `name` | ชื่อ instance ใส่แถวเดียวพอ | ไม่ (ไม่ใส่ = ชื่อไฟล์) |

- ชื่อคอลัมน์ไม่สนตัวพิมพ์เล็ก/ใหญ่ ส่วนแถวว่างระบบจะข้ามให้
- CSV ต้องบันทึกเป็น UTF-8 (ใน Excel เลือก **CSV UTF-8**)
- `.xlsx` ระบบอ่านเฉพาะ sheet แรก
- ตารางไม่มีช่องสำหรับค่า optimal ถ้าต้องการวัด gap ให้กรอกเองในหน้า Benchmark

### ไฟล์ที่ระบบปฏิเสธ

ระบบบอกสาเหตุเป็นภาษาไทย เช่น

- demand ของลูกค้ารายใดรายหนึ่งเกินความจุรถ (ส่งไม่ได้แน่นอน)
- ไม่มี CAPACITY หรือพิกัด หรือไม่พบคอลัมน์ที่จำเป็น

## วิธีคำนวณ

โค้ดทั้งหมดอยู่ใน [backend/app/services/solver.py](backend/app/services/solver.py)

### ภาพรวม

```
ไฟล์ที่อัปโหลด
   │  table_import.py   .csv/.xlsx → แปลงเป็นข้อความ CVRPLIB
   ▼
parse_vrp()             อ่านพิกัด, demand, ความจุ, depot, optimal, จำนวนรถ แล้วตรวจความถูกต้อง
   ▼
distance matrix         ระยะเส้นตรงระหว่างทุกคู่จุด
   ▼
OR-Tools                1) หาคำตอบแรกด้วย PATH_CHEAPEST_ARC
                        2) ปรับปรุงด้วย Guided Local Search จนหมดเวลา
   ▼
total_distance()        ระยะรวมจริงของเส้นทางที่ได้
   ▼
gap                     (ระยะที่ได้ − optimal) / optimal × 100
```

### 1. ระยะทาง

ระยะระหว่างจุดคือระยะเส้นตรง (Euclidean) `√(Δx² + Δy²)` คิดเป็น **ทศนิยมเต็ม** ตามเกณฑ์ของการแข่งขัน

OR-Tools รับเฉพาะจำนวนเต็ม ระบบจึงคูณระยะด้วย 1,000 ก่อนส่งให้ OR-Tools ใช้ค้นหา
แต่ระยะรวมที่แสดงผลคำนวณใหม่จากพิกัดจริงทุกครั้ง ผลจึงไม่มีการปัดเศษสะสม

### 2. จำนวนรถ

1. **จำนวนที่ไฟล์ระบุ** — อ่านจาก `No of trucks` ใน COMMENT หรือเลขหลัง `-k` ในชื่อ
2. **จำนวนขั้นต่ำ** — `ceil(demand รวม ÷ capacity)` น้อยกว่านี้ขนของไม่หมดแน่นอน
3. **จำนวนที่เปิดให้ OR-Tools ใช้**
   - ไฟล์ระบุไว้ → ใช้ค่าที่ระบุ แต่ไม่ต่ำกว่าจำนวนขั้นต่ำ
   - ไฟล์ไม่ระบุ → จำนวนขั้นต่ำ + 1 คัน
4. **รถสำรอง** — บางครั้งจัดของลงรถไม่ลงตัวแม้จำนวนรถจะถึงขั้นต่ำ
   (เช่น ลูกค้าแต่ละรายต้องการ 60 แต่รถจุ 100 คันหนึ่งจึงส่งได้แค่รายเดียว)
   ระบบจึงลองหาคำตอบแรกภายใน 1 วินาที ถ้าหาไม่ได้จะเพิ่มรถสำรอง 3 คัน
   รถสำรองมีค่าปรับต่อคันสูงกว่าระยะทางรวมทั้งหมด OR-Tools จึงใช้รถสำรองน้อยคันที่สุด

จำนวนรถที่ใช้จริงคือจำนวนรถที่มีเส้นทาง รถที่ไม่ได้ออกไปส่งใครไม่นับ

ระบบไม่ได้เปิดรถสำรองไว้ตั้งแต่แรก เพราะรถว่างในโมเดลทำให้ Guided Local Search หาคำตอบได้แย่ลง
(วัดกับ `P-n40-k5` ที่ 5 วินาที: ระยะจาก 458 เป็น 459)

### 3. การค้นหา

| ขั้น | วิธี | หน้าที่ |
|---|---|---|
| คำตอบแรก | `PATH_CHEAPEST_ARC` | สร้างเส้นทางแบบ greedy อย่างรวดเร็ว โดยต่อไปยังจุดที่ใกล้ที่สุดเรื่อย ๆ |
| ปรับปรุง | `GUIDED_LOCAL_SEARCH` | ย้าย/สลับจุดระหว่างเส้นทางซ้ำ ๆ และลงโทษเส้นที่ใช้บ่อยเพื่อหนีคำตอบที่ติดอยู่ใน local optimum |

ค้นหาจนหมดเวลาที่เลือก (5 / 10 / 30 วินาที, API รับ 1–60 วินาที)

ระบบส่ง distance matrix และ demand ให้ OR-Tools เก็บไว้ฝั่ง C++ (`RegisterTransitMatrix`)
แทนการให้ OR-Tools เรียกฟังก์ชัน Python ทุกครั้งที่ต้องการค่า การค้นหาจึงเร็วขึ้นมาก
และในเวลาเท่ากัน Guided Local Search ลองได้หลายรอบกว่า

### 4. Gap

```
gap (%) = (ระยะที่ได้ − optimal) / optimal × 100
```

- ไม่มีค่า optimal → gap = ไม่มี (แสดง "—")
- ค่า optimal ของ CVRPLIB คิดแบบปัดระยะแต่ละเส้นเป็นจำนวนเต็ม แต่ระบบนี้คิดทศนิยมเต็ม
  **gap จึงมากกว่า 0 เล็กน้อยเสมอ** แม้ได้เส้นทางที่ดีที่สุดแล้ว

## API

Base URL: `http://127.0.0.1:8010` · เอกสารแบบกดลองได้: `/docs`

ข้อผิดพลาดทุกกรณีตอบเป็น `{"detail": "ข้อความภาษาไทย"}` พร้อม status code ที่ตรงกับสาเหตุ

### Solver

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| `GET` | `/api/health` | เช็คว่า backend ทำงาน |
| `POST` | `/api/solve` | อัปโหลดไฟล์แล้วคำนวณเส้นทาง |
| `GET` | `/api/samples/{name}` | เนื้อหาไฟล์ตัวอย่าง CVRPLIB |

**`POST /api/solve`** — `multipart/form-data`

| field | ชนิด | ค่าเริ่มต้น |
|---|---|---|
| `file` | ไฟล์ `.vrp` / `.txt` / `.csv` / `.xlsx` | — |
| `time_limit` | จำนวนเต็ม 1–60 (วินาที) | 10 |

```bash
curl -F file=@backend/samples/A-n32-k5.vrp -F time_limit=5 http://127.0.0.1:8010/api/solve
```

```jsonc
{
  "name": "A-n32-k5",
  "capacity": 100,
  "depot": 1,
  "distance": 787.08,          // ระยะทางรวม
  "optimal": 784,              // null = ไม่มีค่า
  "gap": 0.39,                 // %, null = ไม่มี optimal
  "feasible": true,            // ทุกคันบรรทุกไม่เกินความจุ
  "elapsed": 5.0,              // วินาที
  "vehicles_stated": 5,        // จำนวนรถที่ไฟล์ระบุ, null = ไม่ระบุ
  "nodes":  [{ "id": 1, "x": 82, "y": 76, "demand": 0 }, ...],
  "routes": [{ "stops": [25, 28], "load": 44 }, ...]   // 1 รายการ = รถ 1 คัน (ไม่รวม depot หัว/ท้าย)
}
```

| Status | สาเหตุ |
|---|---|
| 400 | ไฟล์ผิดรูปแบบ / ข้อมูลใช้ไม่ได้ |
| 413 | ไฟล์ใหญ่เกิน 1 MB |
| 422 | `time_limit` อยู่นอกช่วง 1–60 / หาคำตอบไม่ได้ในเวลาที่กำหนด |

### Benchmark

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| `GET` | `/api/benchmark/instances` | รายชื่อ instance ในคลัง + จำนวนไฟล์ตัวอย่าง |
| `POST` | `/api/benchmark/instances` | อัปโหลดหลายไฟล์ (field `files`, ครั้งละไม่เกิน 50) |
| `POST` | `/api/benchmark/samples` | เพิ่มชุดตัวอย่าง CVRPLIB เข้าคลัง |
| `DELETE` | `/api/benchmark/instances/{name}` | ลบ instance |
| `PUT` | `/api/benchmark/instances/{name}/optimal` | body `{"optimal": 784}` กรอกค่าเอง / `{"optimal": null}` ลบค่าที่กรอก |
| `POST` | `/api/benchmark/instances/{name}/run?time_limit=10` | รัน instance เดียว (ผลรูปแบบเดียวกับ `/api/solve`) |

การอัปโหลดหลายไฟล์ไม่ล้มทั้งชุดเพราะไฟล์เดียวเสีย ไฟล์ที่ใช้ได้จะบันทึกตามปกติ

```json
{
  "added":  [{ "file": "a.vrp", "name": "A-n32-k5", "replaced": false }],
  "errors": [{ "file": "b.csv", "error": "ไม่พบคอลัมน์ capacity (ต้องมี x, y, demand, capacity)" }]
}
```

ถ้าชื่อซ้ำกับ instance เดิม ไฟล์ใหม่จะแทนที่ของเดิม (`replaced: true`)

## การตั้งค่า

ค่าทั้งหมดอยู่ใน [backend/app/core/config.py](backend/app/core/config.py)

| ค่า | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `ROUTE_DATA_DIR` (environment variable) | `backend/data` | ที่เก็บไฟล์ที่ผู้ใช้อัปโหลด เช่น volume ของ server ตอน deploy |
| `MAX_UPLOAD_BYTES` | 1,000,000 | ขนาดไฟล์สูงสุด (ไฟล์ CVRPLIB ใหญ่สุดยังไม่ถึง 100 KB) |
| `MAX_FILES_PER_UPLOAD` | 50 | อัปโหลดได้ครั้งละกี่ไฟล์ |
| `TIME_LIMIT_MIN / MAX / DEFAULT` | 1 / 60 / 10 | ช่วงเวลาค้นหาที่ API รับ (วินาที) |

ค่าอื่นที่เกี่ยวข้อง

| ค่า | อยู่ที่ | ค่าเริ่มต้น |
|---|---|---|
| คลังเก็บได้สูงสุด | `MAX_UPLOADED` ใน [instance_store.py](backend/app/services/instance_store.py) | 200 ไฟล์ |
| จำนวนจุดสูงสุดต่อไฟล์ | `MAX_NODES` ใน [solver.py](backend/app/services/solver.py) | 2,000 |
| เกณฑ์ gap | `GAP_THRESHOLD` ใน [api.js](frontend/src/lib/api.js) | 5 % |
| ตัวเลือกเวลาค้นหาบนหน้าเว็บ | `TIME_LIMITS` ใน [api.js](frontend/src/lib/api.js) | 5, 10, 30 วินาที |
| พอร์ต backend | [app/main.py](backend/app/main.py) และ proxy ใน [vite.config.js](frontend/vite.config.js) | 8010 |

backend เปิดที่ `127.0.0.1` เท่านั้น (เครื่องอื่นในวง LAN เข้าไม่ได้) เพราะเป็น dev server ที่เปิด auto-reload

## ข้อจำกัด

- รองรับเฉพาะ CVRP แบบพื้นฐาน: ความจุรถ + ระยะทาง ยังไม่รองรับ
  - กรอบเวลาส่งของ (time windows)
  - รถหลายขนาด / หลาย depot
  - ระยะทางตามถนนจริง (ระบบใช้ระยะเส้นตรงจากพิกัด)
  - พิกัดละติจูด/ลองจิจูด (`EDGE_WEIGHT_TYPE: GEO`)
- ผลที่ได้เป็นคำตอบที่ดีที่สุดที่หาได้ในเวลาที่กำหนด ไม่ได้พิสูจน์ว่าเป็นค่าที่ดีที่สุดจริง
- ระหว่างคำนวณ แต่ละคำขอใช้ CPU ของ server จนครบเวลาค้นหา
  หน้า Benchmark จึงรันทีละไฟล์ ไม่รันพร้อมกัน
- ไม่มีระบบผู้ใช้ ทุกคนที่เข้าถึง backend เห็นและแก้คลัง Benchmark เดียวกัน
